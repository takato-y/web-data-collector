## 1. 収集を始める前の確認（必須）

ツールを設定する前に、収集したいサイトごとに次を確認し、記録を残す。1 つでも満たさないサイトは収集しない。

| No | 確認すること | 確認先 |
|---|---|---|
| 1 | 利用規約で、自動的な収集（クローリング・スクレイピング）が禁止されていない | 対象サイトの利用規約 |
| 2 | 収集したいページが robots.txt で禁止されていない（ツールも自動で確認するが、事前に人が読む） | `https://対象サイト/robots.txt` |
| 3 | 公式の API やデータ提供（CSV など）がないか。あればそちらを使う | 対象サイトの案内 |
| 4 | ログインが必要なページ・個人情報を含むページではない | 対象のページ |
| 5 | 収集の頻度と量が、相手の負担にならない（既定は 1 秒に 1 回以下、1 日 2 回程度） | 設定ファイル |
| 6 | 収集した値の使い道が社内での確認に限られ、再配布・公開しない | 社内の取り決め |

対象サイトから停止の依頼があった場合は、ただちに設定ファイルの `targets` から外す。

## 2. 必要なもの

| 項目 | 内容 |
|---|---|
| Node.js | 22 以上（収集部） |
| Python | 3.12 以上（分析部・デモショップ） |
| ディスク | Playwright のブラウザを入れる場合は 200 MB 程度の空き（JavaScript ページを収集しない場合は不要） |
| 通信 | 対象サイトへの HTTPS、通知先への HTTPS |

## 3. 導入

### 3.1 Linux・macOS・WSL

```bash
# 分析部（Python）
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 収集部（TypeScript）。依存は collector/node_modules の中だけに入る
cd collector
npm ci
npm run build
npm run install-browser   # JavaScript ページを収集する場合だけ（ブラウザも collector/node_modules に入る）
cd ..

# 設定ファイルを写して編集する（config.yaml は Git の管理外）
cp config.example.yaml config.yaml
```

### 3.2 Windows

```powershell
py -3.12 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
cd collector
npm ci
npm run build
$env:PLAYWRIGHT_BROWSERS_PATH = "0"; npx playwright install chromium-headless-shell   # 任意
cd ..
Copy-Item config.example.yaml config.yaml
```

Windows での導入手順は記載のみで、実際の導入は未確認。

### 3.3 Webhook の URL

URL は環境変数 `WEBHOOK_URL`（名前は `notify.webhook_url_env` で変更可）で渡す。設定ファイル・スクリプト・crontab に直接書かない。

- Linux: 権限を絞ったファイル（`chmod 600`）に `export WEBHOOK_URL=...` を書き、実行の前に読み込む
- Windows: タスクを実行する利用者の環境変数に設定する

URL を設定していない場合、通知は送らず、変更は未通知のまま残る（設定後の実行でまとめて送る）。

## 4. 設定

`config.yaml` の主な項目は基本設計書 6 章を参照。対象サイトを追加するときは次の順に行う。

1. ブラウザで対象ページを開き、開発者ツールで商品 1 件を囲む要素・商品ID・商品名・価格の位置を調べる
2. `targets` に 1 件追加し、`item_selector` と `fields` を書く。`fields.product_id` は必須（前回と比べる鍵）
3. 在庫の表記が既定（在庫あり・残りわずか・在庫切れ など）と違う場合は `stock_words` に追記する
4. `node collector/dist/src/cli.js collect -c config.yaml --target 追加した名前` で 1 回だけ収集し、取得件数を確認する
5. `.venv/bin/python -m webcollector report -c config.yaml` で帳票を作り、「最新一覧」の中身を確認する

## 5. 実行

| 目的 | コマンド |
|---|---|
| まとめて実行（定期実行と同じ） | `scripts/run.sh config.yaml`（Windows: `powershell -NoProfile -ExecutionPolicy RemoteSigned -File scripts\run.ps1 -Config config.yaml`） |
| 収集だけ | `node collector/dist/src/cli.js collect -c config.yaml` |
| 差分検出だけ | `.venv/bin/python -m webcollector analyze -c config.yaml` |
| 帳票だけ | `.venv/bin/python -m webcollector report -c config.yaml` |
| 通知の内容を送らずに見る | `.venv/bin/python -m webcollector notify -c config.yaml --dry-run` |

初回の実行は「基準」を記録するだけで、変更は検出されない。2 回目以降に変更が検出される。

### 5.1 デモショップで試す

```bash
.venv/bin/python -m demo_site --data demo_site/data/day1.json   # 別の端末で起動（127.0.0.1:8000）
scripts/run.sh config.example.yaml                              # 1 回目
# デモショップを止め、--data demo_site/data/day2.json で起動し直してから
scripts/run.sh config.example.yaml                              # 2 回目（変更を検出）
```

一連の流れを自動で行う場合は `scripts/e2e.sh`（作業用の一時フォルダで実行し、リポジトリ内には何も残さない）。

## 6. 定期実行の登録

### 6.1 cron（Linux）

`scripts/cron.example` を参考に `crontab -e` で登録する。前回の実行が終わっていない場合、次の実行は何もせずに終わる（終了コード 3）。

### 6.2 タスクスケジューラ（Windows）

到達目標: 毎日決まった時刻に `scripts\run.ps1` が動くタスクを作る。

コマンドで作る場合の例（パスは導入先に合わせる。実際の登録は未確認）:

```powershell
schtasks /Create /TN "WebDataCollector" /SC DAILY /ST 08:00 `
  /TR "powershell -NoProfile -ExecutionPolicy RemoteSigned -File C:\tools\web-data-collector\scripts\run.ps1"
```

実行ポリシーは `RemoteSigned` を指定する（インターネットから取得した署名のないスクリプトは実行されない）。全てのスクリプトを無条件に実行する `Bypass` は使わない。zip でダウンロードして展開した場合は、中身を確認したうえで、次のコマンドでダウンロードの印を一度だけ外す。

```powershell
Get-ChildItem C:\tools\web-data-collector\scripts\*.ps1 | Unblock-File
```

置き場所は、タスクを実行する利用者以外が書き換えられないフォルダにする。

画面で作る場合は、タスクスケジューラの「基本タスクの作成」から、操作に上と同じプログラムと引数を指定する。

## 7. 日々の運用

| 作業 | 頻度 | 内容 |
|---|---|---|
| 通知の確認 | 毎回 | 変化があった商品だけが届く。詳細は帳票（`output/report_日時.xlsx`）の「変更一覧」 |
| 実行結果の確認 | 週 1 回 | 帳票の「サマリー」で、状態が「成功」以外の対象がないか確認する |
| ログの確認 | 異常時 | `logs/run_YYYYMMDD.log`（実行スクリプト）、`logs/analysis.log`（分析部） |
| 古いログ・帳票の削除 | 月 1 回 | 必要な期間（例: 3 か月）を残して削除する |
| 履歴DB の控え | 月 1 回 | 実行していない時間に `data/history.db` を別の場所へ写す |

## 8. 困ったとき

詳しい対応は [07_障害対応手順書](07_障害対応手順書.md) を参照する。

| 症状 | 考えられる原因 | 対処 |
|---|---|---|
| 終了コード 2（ERR-001〜ERR-004） | 設定ファイルの誤り | 表示された理由に従って `config.yaml` を直す |
| 終了コード 3（ERR-005） | 前回の実行が終わっていない | 前回の処理（プロセス）がまだ動いていないか確認する。長時間かかる場合は対象や `max_pages` を見直す |
| 状態が「見送り」（ERR-006・ERR-007・ERR-016） | robots.txt を取得できない（404・410 以外の 4xx・5xx・通信エラー）、開始 URL が robots.txt で禁止されている、または JavaScript ページで Playwright がない | 備考欄の理由を確認する。robots.txt で禁止された場合は収集しない |
| 状態が「一部失敗」・「失敗」（ERR-008〜ERR-012・ERR-017） | 一部または全部のページが取得できない・ページ数の上限に到達・JavaScript ページを描画できない | ログの ERROR 行を確認する。一部失敗・失敗の回では掲載終了を判定しない |
| 状態が「失敗」で備考が `商品が 0 件（前回 <件数> 件）`（ERR-022） | サイトの作りが変わり、セレクタが合わなくなった | 4 章の手順でセレクタを直す。この回は掲載終了を判定しない |
| 状態は「成功」だが取得件数が急に減った | 一部の商品だけセレクタが合わなくなった | 4 章の手順でセレクタを直す。減った分が掲載終了として通知されることがある（07_障害対応手順書.md 5.1 節） |
| 価格が空になる（ERR-015） | 価格の表記が想定と違う | `fields.price` のセレクタが価格だけを指しているか確認する |
| 通知が届かない（ERR-020・ERR-021） | URL 未設定・送信先の誤り | ログの「通知を送りません」（URL 未設定・http の外部 URL。ERR-020）、「通知が受け付けられません」（送信先が 2xx 以外）・「通知を送れません」（通信エラー）（ERR-021）を確認する。`notify --dry-run` は内容を表示するだけで URL を使わない。未送信の変更は次回に送られる |
| Excel で商品名の先頭に ' が付いている | 数式として実行されないようにした結果（仕様） | そのまま利用する |

## 9. 定期点検

7 章の日々の運用に加えて、次を確認する。

| 時期 | 確認すること | 確認の方法 |
|---|---|---|
| 毎日（実行のたび） | 実行スクリプトの終了行の値と、ERROR の行の有無 | `logs/run_YYYYMMDD.log` の `===== 終了 (収集=<コード>, 分析=<コード>) =====`（07_障害対応手順書.md 3.1・3.2 節） |
| 毎日（実行のたび） | その日の実行が動いたか（ログのファイルと `===== 開始` の行があるか） | `logs/` の一覧（07_障害対応手順書.md 5.2 節） |
| 毎月 | 対象ごとの取得件数が急に減っていないか（状態が「成功」のまま商品を読み取れなくなっていないか） | 07_障害対応手順書.md 3.5 節の SQL の `items_collected` |
| 毎月 | 未通知の変更が溜まっていないか | 07_障害対応手順書.md 3.5 節の SQL（`notified_at IS NULL` の件数） |
| 毎月 | 状態が「見送り」「一部失敗」のまま続いている対象がないか | 帳票の「サマリー」、07_障害対応手順書.md 3.5 節の SQL |
| 変更時（設定） | 追加・変更した対象だけで収集し、取得件数と帳票の中身を確認する | 4 章の手順 4・5 |
| 変更時（対象サイトの追加） | 1 章の確認（利用規約・robots.txt・公式の API の有無）を行い、記録を残す | 1 章 |
| 変更時（プログラム・部品の更新） | 自動テストが全件合格するか | `cd collector && npm test`、`.venv/bin/python -m pytest`（05_テスト仕様書.md） |

## 10. バックアップと戻し方

| 対象 | 内容 | 控えの取り方 | 戻し方 |
|---|---|---|---|
| 履歴DB（`data/history.db`。場所は `storage.db_path`） | 収集の履歴・商品・変更・通知済みの印。前回との比較に使う | 実行していない時間に別の場所へ写す（7 章。月 1 回） | 1. 定期実行を止める（cron の行を外す・タスクを無効にする） 2. 控えを `data/history.db` に写す 3. 定期実行を戻す。控えより後の実行の記録は失われる。次の実行は控えの時点の値と比べるため、控えより後に通知済みの変化がもう一度検出・通知されることがある |
| 設定ファイル（`config.yaml`） | 収集の対象・セレクタ・通知の形式。Git の管理外のため、リポジトリからは戻せない | 変更のたびに、利用者以外が読めない場所へ写す | 控えを写す。Webhook の URL は含まれない（3.3 節） |
| 環境変数を書いたファイル（Webhook の URL） | 秘密の値 | 控えを取らない | 控えから戻さず、通知先で Webhook を発行し直す（11 章） |
| 帳票（`output/`）・ログ（`logs/`） | 履歴DB から作り直せる（帳票）、調査用の記録（ログ） | 控えの要否・保管期間は運用で決める項目 | 帳票は `.venv/bin/python -m webcollector report -c config.yaml` で最新の状態を作り直す（過去の時点の帳票は作り直せない） |
| プログラム | `collector/`・`webcollector/`・`scripts/`・`sql/` | Git のリポジトリ（版ごとのタグ） | `git checkout <タグ>` で戻し、3 章の手順で導入し直す |

## 11. 資格情報・鍵・トークンの更新

このツールが持つ秘密の値は Webhook の URL だけである。対象サイトへのログインは行わないため、対象サイトの資格情報は持たない。

| 資格情報 | 保管場所 | 更新する場面 |
|---|---|---|
| Webhook の URL | Linux は権限を絞ったファイル（`chmod 600`）の `export WEBHOOK_URL=...`、Windows はタスクを実行する利用者の環境変数（3.3 節）。設定ファイル・スクリプト・crontab・リポジトリには置かない | URL が漏れた可能性があるとき（設定ファイルに書いていた：07_障害対応手順書.md 4.4 節）、通知先で Webhook を消した・発行し直したとき（同 4.21 節）、担当者の交代時 |

更新の手順：

1. 通知先のサービスで新しい Webhook を発行する
2. 保管場所の値を新しい URL に書き換える（値を画面・ログ・チャットに貼らない）
3. 値を読み込んだ端末で `printenv WEBHOOK_URL > /dev/null && echo 設定あり` を実行し、値を表示せずに設定されていることを確認する（環境変数の名前は `notify.webhook_url_env` に合わせる。`--dry-run` は URL を使わないため、この確認にはならない）
4. 次の実行で `[通知] sent` または `[通知] nothing` が出力されることを確認する（`[通知] skipped` が出力された場合は URL が渡っていない。07_障害対応手順書.md 4.20 節）
5. 通知先のサービスで古い Webhook を無効にする

更新の頻度は運用で決める項目とする。

## 12. 連絡体制

| 役割 | 担うこと | 連絡する相手 |
|---|---|---|
| 利用者（通知・帳票を受け取る人） | 通知が届かない、掲載終了が大量に届いたなど、普段と違うことに気付いたら伝える | 運用担当者 |
| 運用担当者 | 07_障害対応手順書.md の 3・4 章で切り分けと対処を行う。対象サイトからの停止の依頼を受けたら、ただちに収集を止める。障害を記録する（同 6 章） | 保守担当者 |
| 保守担当者 | 想定外の誤り（ERR-018・ERR-019）の調査、セレクタ・プログラムの修正、自動テストでの確認 | — |

各役割の担当者・連絡手段・連絡までの目安の時間は運用で決める項目とし、この文書には書かない。
