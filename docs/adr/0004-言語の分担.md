## 背景

当初はすべてを Python で作っていた。収集（Web ページの取得・解析・ブラウザ操作）と、分析・帳票（差分・Excel・通知）では、得意な部品がそろっている言語が異なる。また、利用者の環境によっては収集だけ別のサーバーで動かしたい場合がある。

## 決定

- 収集部は TypeScript（Node.js）で作る。HTTP 取得は Node.js 標準の fetch、HTML 解析は cheerio、JavaScript ページは Playwright、robots.txt の解釈は robots-parser、履歴DB への書き込みは better-sqlite3 を使う
- 分析部（差分検出・Excel レポート・Webhook 通知）は Python で作る
- 2 つの部は直接呼び合わず、SQLite の履歴DB を介して受け渡す。テーブル定義は `sql/schema.sql` の 1 か所に置き、両方の部が起動時に適用する
- 列ごとに書き込む部を 1 つに決める（基本設計書 2.2）
- Python で作っていた収集処理は、TypeScript 版で置き換えた時点で削除する（収集処理を 2 つ持たない）

## 比較した案

| 案 | 長所 | 短所 |
|---|---|---|
| すべて Python | 1 言語で済む | Playwright の情報・事例は Node.js 版が多い。非同期の取得を書くと複雑になる |
| すべて TypeScript | 1 言語で済む | Excel のグラフ・書式を細かく指定できる部品の選択肢が Python より少ない |
| 分担し、HTTP API で受け渡す | 部を別のサーバーに置ける | 受け渡しのためのサーバーを常時動かす必要があり、この規模には過剰 |
| **分担し、SQLite で受け渡す（採用）** | 各部が得意な部品を使える。受け渡しの形がテーブル定義として文書に残る。サーバーが要らない | 2 つの実行環境（Node.js と Python）の導入が必要。同時実行を避ける運用が要る |

## 影響

- 導入手順に Node.js と Python の両方が必要になる（06_導入・運用手順.md）
- テーブル定義の変更は両方の部に影響するため、変更時は両方のテストを流す
- 一連の確認（収集 → 分析）は、両方の言語をまたぐ通し試験で行う（05_テスト仕様書.md）
