## 背景

ADR-0003 は「判断に迷う場合は、取得しない側・通知しない側に倒す」と決めた。ところが実装には、この方針から外れる箇所が 2 つあった。

- robots.txt の取得が 4xx で終わると、401・403（アクセスを断られている）や再試行しても続いた 429（混雑）でも「robots.txt が無い」とみなし、制限なしで収集していた。取り決めを確かめられていないのに取得する側に倒れていた
- 一覧ページは取得できたのに、対象サイトの作りが変わってセレクタが合わず商品を 1 件も読み取れない回が、エラー 0 件のため「成功」になっていた。成功の回は掲載終了を判定するため、前回まで掲載中だった全商品が掲載終了として記録・通知されていた

## 決定

| 場面 | 扱い |
|---|---|
| robots.txt が 404・410 | robots.txt が無いものとして、制限なしで扱う（ADR-0003 から変えない） |
| robots.txt が 404・410 以外の 4xx（400・401・403・再試行後の 429 など） | 5xx・通信エラーと同じく、そのサイトの収集を今回は見送る |
| 商品が 0 件（エラー 0 件）で、同じ対象の直前の成功・一部失敗の回に商品があった | 読み取りの失敗とみなしてエラーとして数え、状態を「失敗」にする。失敗の回は掲載終了を判定しない |
| 初回、または直前の成功・一部失敗の回も 0 件 | 比べる相手が無いため、これまでどおり「成功」とする |

- 状態の決め方は収集部（`collector/src/collector.ts`）の 1 か所にまとめる。分析部は従来どおり「成功の回だけ掲載終了を判定する」（`webcollector/diff.py`）。同じ判定を両方の部に書くと、片方だけ直したときに食い違うため、分析部には足さない
- 直前の回の商品件数は履歴DB の `collection_runs.items_collected` から読む（`Storage.lastItemCount`）。失敗・見送り・実行中の回は見ないため、0 件の「失敗」が続いても、最後に商品が取れた回の件数と比べ続ける

## 比較した案

| 案 | 採らなかった理由 |
|---|---|
| 分析部の差分検出で、商品 0 件なら掲載終了を出さない | 状態は「成功」・終了コード 0 のまま残り、帳票と終了コードから異常に気付けない |
| 新しい状態（例：`empty`）を追加する | 履歴DB の CHECK 制約（`sql/schema.sql`）の変更が要り、既存の履歴DB には `CREATE TABLE IF NOT EXISTS` では反映されない。既存の「失敗＝1 件も取れない」の定義で表せる |
| 「一部失敗」にする | 一部失敗は「商品は取れたが一部のページで誤りがあった」の意味で使っている。商品が 0 件の回は失敗の定義に当てはまる |
| robots.txt の 4xx をすべて制限なしとする（以前の動き） | アクセスを断られているときに収集を続けることになり、ADR-0003 の「迷ったら取得しない」に反する |

## 参考

robots.txt の取り扱いを定める RFC 9309 は、4xx（"Unavailable"）では取得してよい（MAY）、5xx・通信エラー（"Unreachable"）では全体を禁止とみなす（MUST）としている。本決定は 404・410 以外の 4xx でも見送るため RFC より取得しない側に寄っているが、RFC は 4xx での取得を義務にはしていないため矛盾しない。

- 出所：<https://www.rfc-editor.org/rfc/rfc9309.html> 2.3.1.3 節・2.3.1.4 節（確認日 2026-11-16）

## 影響

- 401・403・429 を返すサイトは、robots.txt を取得できるようになるまで毎回「見送り」になる（ERR-006）
- 対象サイトの商品が本当に 0 件になった場合は、毎回「失敗」になり掲載終了も記録されない。運用担当者が収集を続けるか対象から外すかを決める（07_障害対応手順書.md 4.22 節、ERR-022）
- 商品が 0 件ではなく減っただけの回は、これまでどおり「成功」として掲載終了を判定する（07_障害対応手順書.md 5.1 節）
